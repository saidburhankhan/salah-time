# Architecture review

Scope: branch `items-mvp`, reviewed 2026-11-22. This is a structural review, not a claim that the current MVP is unusable. The single `src/` directory is a symptom; the material problem is that one crate cannot enforce dependency direction or isolate effects.

## Findings

| Severity | Finding and evidence | Risk | Fix direction |
|---|---|---|---|
| **High** | The dependency graph crosses layers in both directions: `item` imports `schedule::BlockKey` (`src/item.rs:8-9`), `planner` imports the concrete `Store` and schedule (`src/planner.rs:5-12`), `status` imports planner DTO `Today` (`src/status.rs:1-4,70-77`), while planner calls status formatting (`src/planner.rs:762-766,818-822`). Quick parsing also returns an application command (`src/quick.rs:4-6,19-20`). | Domain, presentation, persistence, and use cases cannot evolve or be tested independently; extracting integrations will amplify cycles. | Put domain types/rules in a dependency-free crate; make application depend on domain and port traits; put JSON DTO/formatting outside both. |
| **High** | `schedule::prayers_for` silently reads the official filesystem cache (`src/schedule.rs:113-140`; `src/official.rs:144-157`). `schedule` therefore mixes policy, calculation, and I/O despite callers treating it as deterministic. | Tests depend on ambient XDG/HOME state; identical inputs can produce different schedules; a future daemon/sync worker can race cache changes. | Inject a `PrayerSource` port returning provenance; keep selection policy in application and cache I/O in an adapter. |
| **High** | Time zones are stored as an `f64` UTC offset (`src/config.rs:13,40,62-63`) and converted to `FixedOffset` (`src/schedule.rs:95-97,143-149`; duplicated at `src/main.rs:1027-1029`). | DST and historical/future civil-time changes are wrong outside fixed-offset regions; scheduled events and integrations can shift by an hour. | Store an IANA zone ID, use `chrono-tz`/equivalent, keep UTC instants plus local date/time/zone, and define ambiguous/nonexistent-time policy. |
| **High** | The CLI JSON is the application API, but only status has a version (`src/status.rs:53-54,91-95`). `day`, stats, items, config, mutation results, and errors have no envelope/version; the app accepts almost any JSON object (`app/src/backend.cpp:74-79,104-124`). The redesign contract documents shapes but is not machine-checked. | A Rust field rename/additional enum or mixed binary/UI install can silently corrupt UI assumptions. Telegram/Slack clients would multiply this compatibility surface. | Introduce versioned request/response DTOs and a common envelope/error code; generate fixtures/schema and consumer contract tests for every UI-used command. |
| **High** | Multi-process writes rely only on SQLite WAL and a three-second busy timeout (`src/store.rs:172-191`). Each UI action spawns a fresh CLI process (`app/src/backend.cpp:39-50,153-166,190-218`; `plugin/local.salah/BarWidget.qml:97-113,173-178`), and read-modify-write rules such as `next_position` load all rows before a later write (`src/planner.rs:85-94`). | App, widget, terminal, and future integrations can contend, time out, or make stale decisions; WAL helps readers but does not serialize application invariants. | Make mutations atomic in repository transactions with DB constraints; add lock/retry classification now, then make a single daemon the writer when integrations arrive. |
| **High** | Sync identity/conflict semantics are insufficient. IDs/timestamps/tombstones exist, but import is only last-write-wins on `updated_at`; domain events, device/actor identity, causal revision, idempotency keys, and an outbox are absent (`src/store.rs:15-61`; `src/export.rs:121-178`). | Cloud sync and webhook retries can lose concurrent edits, duplicate side effects, or resurrect/delete data incorrectly. | Add aggregate revisions and an append-only event/outbox record in the same transaction; define conflict rules per aggregate before remote sync. |
| **Medium** | `planner.rs` is a 1,477-line application god module spanning CRUD, timers, reports, prayer marks, day projection, history, and stats; `main.rs` is 1,046 lines spanning clap definitions, orchestration, JSON/human rendering, filesystem export, config, location, and official sync (`src/planner.rs:1-15`; `src/main.rs:427-442,539-724,855-1045`). | Changes have wide review/test blast radius and create merge conflicts; ports cannot be introduced locally. | Split by use case and projection, then make CLI handlers thin adapters; crate extraction should follow these seams. |
| **Medium** | Errors are strings across domain, storage, application, and transport (`src/item.rs:46,158,175,207`; `src/store.rs:84-85,173-223`; `src/planner.rs:86-101`; `src/main.rs:427`). | Callers cannot distinguish validation, conflict, unavailable source, busy DB, or internal failure except by parsing prose; retry and HTTP/IPC mapping are unsafe. | Define typed errors per layer with stable public error codes and sources; stringify only at the CLI/UI boundary. |
| **Medium** | Clock/ID/environment effects are hard-coded: UUID generation in planner (`src/planner.rs:22-30`), `Utc::now()` in CLI (`src/main.rs:463-482`), official parser stamps the clock (`src/official.rs:59-92`), location uses local/UTC clocks and environment (`src/location.rs:215-231,292-306`), and config temp naming uses `SystemTime` (`src/config.rs:129-156`). | Deterministic boundary, retry, timer, and sync tests require special paths or cannot cover failure modes. | Add `Clock`, `IdGenerator`, configuration/path, and source ports; parsing must receive metadata rather than read clocks. |
| **Medium** | Network and filesystem concerns sit in core modules: `official` executes `curl`, caches, parses, and timestamps (`src/official.rs:1-7,59-157`); `location` executes providers, reads Weather state, locks, mutates config, and throttles (`src/location.rs:149-199,206-231,256-321`); `config` owns XDG resolution and atomic writes (`src/config.rs:90-161`). | Provider replacement, offline tests, permissions, telemetry, and daemonization require editing business modules. | Move HTTP, cache, config, and OS discovery to adapters behind narrow ports; retain pure validators/parsers near source models. |
| **Medium** | Presentation/business logic is duplicated. Rust formats durations and schedule times (`src/status.rs:214-239`), the widget recalculates duration/timer display and occurrence weekdays (`plugin/local.salah/BarWidget.qml:48-87,633-669`), and the app optimistically reproduces timer accumulation and item mutations (`app/src/backend.cpp:169-218,231-258`). | Clients drift on timezone, rounding, recurrence, and optimistic rollback; adding mobile/chat clients repeats rules. | Return authoritative projections and mutation results/revisions; restrict clients to display formatting and reconcile optimistic state by command ID. |
| **Medium** | Process spawn is the only API: every refresh runs day/stats/config commands (`app/src/backend.cpp:104-124`), while widget actions queue `salah` invocations (`plugin/local.salah/BarWidget.qml:90-113`). | Startup/parsing overhead, polling, no push updates, no shared transaction/session, weak cancellation, and no integration subscriptions. | Keep CLI compatibility, but define a transport-neutral application API and later host it in a per-user daemon over a versioned local socket. |
| **Medium** | The concrete `Store` exposes persistence vocabulary directly to use cases and serializes enum names as DB values (`src/store.rs:110-123`; `src/planner.rs:86-126`). | Storage migrations and domain vocabulary are coupled; alternate stores or remote sync cannot implement a stable port cleanly. | Define capability-oriented repositories/unit-of-work in application; map explicit persistence records in the SQLite adapter. |
| **Medium** | Official source selection is string-based (`method == "uzbekistan"`, location contains “tashkent”) (`src/schedule.rs:115-121`; `src/main.rs:1019-1028`). | Localization/renaming can select the wrong source; multiple regions/providers cannot be modeled reliably. | Use typed `LocationId`, `CalculationMethodId`, and provider coverage rules, never display-name substring checks. |
| **Low** | Public modules are all re-exported flat (`src/lib.rs:1-12`), exposing accidental APIs and making ownership unclear. | Internal refactors become semver-like changes and newcomers lack a dependency map. | Use crate boundaries plus private modules; export a deliberate domain/application surface. |
| **Low** | Several invariant failures are hidden or coerced: date overflow falls back to the original date (`src/schedule.rs:90-93`), schedule lookup failures become `None` while closing timers (`src/planner.rs:46-51,104-110`), and status uses `expect` for “validated” configuration (`src/status.rs:174-180`). | Rare bad dates/config/source failures can yield plausible but wrong plans instead of diagnosable errors. | Preserve typed failures through use cases; use explicit validated value objects and never silently skip timer closure. |

## What is already sound

- Prayer calculation is substantially deterministic and separated (`src/calculation.rs`), and item rules state their intent to avoid storage/clocks (`src/item.rs:1-9`). These are useful extraction seams.
- SQLite uses append-only migrations, tombstones, transactions, WAL, and a busy timeout (`src/store.rs:15-65,172-235`); preserve these strengths while tightening atomic invariants.
- The CLI and QML use fixed argument arrays rather than a shell, and JSON already provides a viable compatibility bridge during migration.
- Tests cover core, CLI, planner, and export behavior; the migration can use characterization tests rather than a rewrite.

## Priority conclusion

Moving the same files into folders would not solve the architecture. First stabilize the transport contract and introduce typed boundaries; then split the application god module; then extract pure domain and prayer crates. A daemon is justified when push updates/integrations begin, not as the first refactor.
