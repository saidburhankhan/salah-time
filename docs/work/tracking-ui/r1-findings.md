# R1 findings (tracking-ui phase 2: 62c28b4, 22ec4c3, 029912a)

- [medium] plugin/local.salah/BarWidget.qml:68 (029912a; SessionLogic.js:138, SessionPanel.qml:124) — the pause panel's Worked value is `now - started_at`, but `session.stop` cuts a timer off at its day's Sleep boundary (running.rs `finish`: `ended = now.min(day_end)`) and allows `minutes` only up to that cut-off. For a stale timer the panel shows far more minutes than the server will take, and its local range check uses the same wrong figure — confirmed on 22ec4c3 with Sleep at 23:00: start at 21:00, stop at 07:00 the next day; the widget shows Worked 600, the −30 chip gives 570, Save returns "minutes must be between 1 and 120". A plain Save stores 120 while the panel showed 600. That is the "forgot to pause" overnight case the field exists for — suggested fix: when `running.stale` (or in general), work out elapsed against the clamped end: have `status.get` return the clamped `elapsed_minutes`/`ends_at` for the running session, and use it for both the shown value and the range check.
- [medium] crates/salah-core/src/items.rs:217-221 (22ec4c3) — `item.edit` throws away a `metric_ids` sent in the same request as a project change: `if item.project_id != previous_project { item.metric_ids = None } else if let Some(ids) = changes.metric_ids {...}`. It returns success with nothing to show the selection was ignored — confirmed: `item.edit {id, project_id: P, metric_ids: ["focus"]}` returns `metric_ids: null` and metrics focus/quality/distractions. The app's item editor sends exactly this request when the user picks a project chip and then toggles its "Asks" chips before saving, so the user's choice is silently lost — suggested fix: reset to `None` only when the project changes and `changes.metric_ids` is absent; otherwise check the given list against the new project with `checked_metric_ids` and store it.
- [low] crates/salah-core/src/sessions/running.rs:84-139 (22ec4c3) — `bump` and `append_note` accept a stale timer (still running after its day's Sleep boundary). They write onto that earlier day's session at `now`, and a later stop then sets `ended_at` to the Sleep boundary, before the note — confirmed: timer started 21:00, Sleep 23:00, `session.note` at 08:00 the next day, then stop → session day 2026-11-24, ended 18:00Z, with a note `at` 03:00Z on the 25th and distractions 1. The widget shows "08:00 morning thought" under a 21:00–23:00 session, and the bar "+" still counts into yesterday — suggested fix: reject bump/note on a stale timer with a validation error telling the user to stop it first (or have the bar hide "+" when `running.stale`).
